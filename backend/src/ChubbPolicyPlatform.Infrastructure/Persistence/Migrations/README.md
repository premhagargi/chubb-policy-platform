# Migrations — status and what to verify once the SDK is available

No `dotnet` SDK was available in the environment this repo was authored in. `20260903000001_InitialCreate.cs`
(the actual `Up`/`Down` migration, in this folder) **was hand-written** rather than
generated by `dotnet ef migrations add`, and matches `PolicyConfiguration` column-for-
column. This is plain, reviewable C# — no different in kind from any other hand-written
class — and `Database.Migrate()` (which `Program.cs` calls on startup) only needs
compiled `Migration`-derived classes to apply, not a model snapshot, so this should be
sufficient to boot the app and run the integration tests against a real Postgres.

**What's deliberately *not* here**: the `.Designer.cs` and
`ApplicationDbContextModelSnapshot.cs` companion files `dotnet ef migrations add` would
normally also generate. Those encode exact EF Core/Npgsql metadata annotations design-
time tooling uses to *diff* the model when generating the *next* migration — they are
not needed to apply this one, and hand-authoring their exact format correctly without a
compiler to check it was judged too risky to be worth it.

**Before adding any future migration**, run this once (from `backend/`) to let real
tooling generate the missing snapshot and confirm it agrees with the hand-written one
above:

```bash
dotnet tool install --global dotnet-ef   # if not already installed
dotnet ef migrations add InitialCreate --output-dir Persistence/Migrations/ \
  --project src/ChubbPolicyPlatform.Infrastructure \
  --startup-project src/ChubbPolicyPlatform.Api
```

If it reports the model already matches (no changes / adds only the snapshot), the
hand-written migration was correct. If it wants to add columns/indexes, that's a real
discrepancy to review before trusting `docker-compose up` in production use.
